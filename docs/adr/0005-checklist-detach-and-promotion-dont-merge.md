# A Checklist detaches on its first edit, and promotion copies out without adopting the new reference

An Anchor or Flex holds `checklist` (a Library Checklist id, or `None`) and `checklist_items` (its own literal rows, or empty), with the invariant that at most one is non-empty. `_apply_item_checklist` in `tomorrow/session.py` is the single place this pair is written. The first time the rows editor is saved with content that differs from the referenced Checklist's current rows, it clears `checklist` to `None` and stores the edited rows as `checklist_items` — the item's own literal copy from that point on. There is no per-Session override sitting alongside the reference, and no marker recording that a detach happened or what it detached from; a detached item looks exactly like one that always held literal rows. Re-saving rows that verbatim match the referenced Checklist's current rows is not a detach — `_apply_item_checklist` leaves the reference attached in that case, since nothing was actually edited.

Promotion is a separate, one-way move in the other direction. `promote_checklist` takes an item holding literal rows and a name, rejects the name if its slug already exists in the Checklist library, and otherwise calls `save_checklist` to write a new Library Checklist file from those rows. It does not read the Session item again afterward, and does not rewrite `checklist`/`checklist_items` on it. The item keeps its literal rows and has no idea a Library Checklist now shares its content.

**Why:** Detach-on-first-edit keeps one rule and no new state, matching this codebase's existing precedent that a Day Template seeds a Session rather than merging with it (ADR 0004) — editing a Checklist's rows for one night is likewise a one-time seed away from the Library, not a standing override to reconcile against future Library edits. Skipping a provenance marker avoids an ambiguous middle state: an item's checklist is either a live reference or its own rows, never a reference remembering that it used to point somewhere. Promotion not adopting the new reference keeps promotion a pure "save for later" action: it cannot disturb a Session the planner has already got right, and it avoids a flip-flop where adopting the reference would immediately be detached again by the next keystroke in the rows editor — the item was just edited into literal rows moments before promotion is likely to be reached for.

**Considered:** a diff/merge model that would keep the Library reference on the item while layering a per-Session override of individual rows on top, resolved against the Library Checklist's current rows at render or submit time — rejected as new state and new merge semantics with no existing precedent in this codebase, and because it raises questions (what does "detached" even mean if the reference is still there? does a later Library edit reappear underneath the override?) that a single detach rule never has to answer. Also considered: having promotion adopt the newly created Checklist onto the Session item, rewriting `checklist` to the new id and clearing `checklist_items` — rejected because it would silently reintroduce the reference the planner had just edited away from, and because the very next edit to the rows editor would detach it right back, making the adoption pointless churn rather than a stable outcome.
